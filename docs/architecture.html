1. High-level overview

Kastrup is a single Rust binary that aggregates messages from many transports (email, Slack, IRC, Discord, RSS, etc.) into one unified inbox stored in a local SQLite database. The TUI reads from that database; background threads write to it.

The hot path for chat is the weechat-relay supervisor: a long-lived TCP connection to a remote weechat process on remote relay host that proxies Slack, IRC, Discord-bridge, Matrix, etc. Kernel TCP keepalives detect drops; userspace is parked on read() when idle, so the cost when no traffic is flowing is essentially zero.

Everything else (email/maildir, RSS, Slack-via-API polling, Discord-via-bot polling) runs through a single shared poller thread on per-source intervals.

3. Receive flow

External services land messages in kastrup via three mechanisms:

  1. Push — the weechat-relay supervisor maintains a long-lived TCP socket; updates arrive as binary protocol events.
  2. Poll — the poller thread wakes on intervals and calls source-specific sync_* functions.
  3. Bridge — external programs (gmail-idle, ws-bridge) write to ~/Maildir; the maildir poller picks them up on its next tick.

Why the weechat-relay path is special: chat traffic is bursty and continuous. A 2-minute poll either misses messages or runs constantly. The push connection wakes the thread only when bytes arrive on the socket; an idle remote relay host generates ~zero kastrup wakeups. Kernel TCP keepalives (every 30s, 4 retries × 15s ≈ 90s death detection) live entirely in the kernel — they never wake userspace unless the peer is actually dead.

Slack split: when replying to a message whose folder starts with python.slack., kastrup builds a .slack draft and routes through the Slack Web API instead of the relay's input command. Reason: wee-slack auto-closes inactive DM buffers, and the relay silently drops input targeted at non-existent buffers. The Web API works against the workspace regardless of which buffers are open.
Why Slack send avoids "via wee-slack" badge: with the xoxc/xoxd cookie pair (the same auth wee-slack itself uses internally), Slack treats the post exactly like a web-typed message. No app attribution. The legacy xoxp- fallback still works but Slack tags every message "via wee-slack" because the token belongs to the wee-slack public Slack app.

Token loading order for Slack send:
  1. If SLACK_API_TOKEN is set in ~/.kastrup/.env, use it (plus SLACK_API_COOKIE if also set).
  2. Else, parse ~/.weechat/plugins.conf for the comma-separated python.slack.slack_api_token list.
  3. From that list: prefer the xoxc-…:xoxd-… pair if present (sets both bearer and cookie).
  4. Otherwise fall back to the first xoxp-… entry (bearer only).

7. Threads & shared state

main thread ──────► render TUI, dispatch keys
   │
   ├─► messages_dirty: Arc<AtomicBool>     flipped by writers, read by 5s tick
   ├─► nick_lists: Arc<Mutex<HashMap<>>>   per-buffer nicks (supervisor writes)
   ├─► subscribed_buffers: Arc<Mutex<Vec>> open weechat buffers (supervisor writes)
   ├─► write_tx: mpsc::Sender<DbWriteOp>   serialized writes to DB writer thread
   │
   ├──► Poller thread (start_poller)       2-min/5-min ticks per source
   │      └─► db.insert_messages_batch + db.update_source_sync_time
   │
   ├──► DB writer thread                   owns one rusqlite Connection
   │      └─► drains write_rx: MarkRead, ToggleStar, DeleteMessages,
   │            UpdateFolder, UpdateMetadata, MarkAllReadBulk, …
   │
   └──► weechat-relay supervisor           one supervised long-lived TCP socket
          └─► db.insert_message / insert_messages_batch on each _buffer_line_added
          └─► nick_lists / subscribed_buffers updates

Why a dedicated DB writer thread?

Rusqlite is serial — only one writer at a time. With multiple threads doing mutations (mark-read, toggle-star, batch insert from poller, batch insert from supervisor), we'd contend on the connection mutex. Funneling all writes through a single thread + mpsc channel keeps each writer thread non-blocking, lets the main thread fire-and-forget user mutations, and means the connection's transaction handling is owned by one place.

8. Views, sorting, ordering

Views are filter recipes stored in the views table. Each view has a filters JSON blob with a rules array of {field, op, value}. The rule parser honors op = "=" (exact match) and op = "like" (pipe-OR LIKE %v%).

Per-view settingStorage keyPurpose
Thread modethread_mode_<key>flat / threaded / folders
Pinned section ordersection_order_<key>JSON array, channels listed here rank above unpinned
Hidden channelshidden_channels_<key>JSON array, channel folders excluded from Folders view

Default channel sort (Folders mode) is by latest message timestamp, descending. Pinned channels rank above unpinned in section_order order; unpinned channels stay newest-first below.

Folders-view merge (v0.1.105+)

The Folders mode shows every subscribed weechat buffer that matches the current view's folder filter, even if it has no messages in the loaded 500-message window. The supervisor publishes its current buffer registry to a shared SubscribedBuffers snapshot; rebuild_display unions that with message-derived sections.

This means a quiet channel like #cab with all messages older than the load-limit window still appears as a section ([0] count). The user can mark it read or hide it (Ctrl+K) just like any other.

9. Dedup & the weechat-relay hash

Messages dedupe on (source_id, external_id) UNIQUE. For most sources the external_id is provided by the transport (Slack message timestamp, RSS GUID, maildir filename, etc.). For weechat-relay there's no stable line ID across weechat restarts, so kastrup synthesizes one: 

weechat-relay_<md5(folder│timestamp│message-head[0..80])>

This was changed from a previous formula that included the nick in the hash. Some DB rows from before the change still carry old-format external_ids; to avoid a reconnect re-inserting them under the new hash, the supervisor checks both the new hash AND the legacy (folder│ts│nick│msg-head) hash against known_ids before inserting. New rows get the new hash; legacy rows match on either.

10. Design principles

The three rules, in priority order:

  1. No wasted CPU cycles. Every feature is gated. Compare desired state to last-applied state before doing X11/syscall/network work. The supervisor's read() is kernel-parked — zero userspace cycles when no chat is happening.
  2. Lightning fast. No interpreters in helper scripts. Cache anything stable. The 5s message-refresh tick is gated on a messages_dirty atomic so idle kastrup doesn't run get_messages() for no reason.
  3. More battery life. A consequence of the first two. The previous 6-min idle reconnect (read timeout) used to wake up every 6 min for the entire chat-quiet workday — removed in v0.1.103 in favor of kernel keepalives only.

Other rules

  • No secrets in tracked source files. Real tokens live in ~/.kastrup/.env (chmod 600). Patterns in code use only prefixes like "xoxp-", never literal token bytes. Pre-commit sweep before every push.
  • Backward-compat on hash changes. Never re-duplicate existing DB rows just because a derivation formula changed.
  • Send paths are transport-specific. One generic "send anything" abstraction would be vague and brittle. Slack/Discord/Weechat each have their own send_*_draft function with explicit auth handling.
  • The TUI is just a reader. All mutation (insert, mark-read, delete) goes through the DB writer thread. The main thread never blocks on a DB write.
